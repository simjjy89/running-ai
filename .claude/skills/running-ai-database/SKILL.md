# RunningAI database rules

Follow `running-ai-dev` for the general workflow; this skill adds the persistence rules.

## Ownership

- **PostgreSQL 17** is the local/runtime database (`docker-compose.yml` at the root,
  `local` profile, `DB_URL` / `DB_USERNAME` / `DB_PASSWORD`; `.env` is a fallback).
- **Flyway owns the schema.** Hibernate runs with `ddl-auto: validate` in every profile
  and only checks that entity mappings match the migrated schema.
- **Applied migrations are immutable.** Never edit
  `V1__create_athlete.sql`, `V2__create_activity.sql`, `V3__create_activity_raw.sql`
  (`server/src/main/resources/db/migration/`). Any schema change is a new
  `V<N>__<snake_case_description>.sql`, plus the matching entity change, plus tests.
- Migrations are plain SQL that must run on PostgreSQL **and** on H2 in PostgreSQL mode
  (tests). Use `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `VARCHAR(n)`, `INTEGER`,
  `DOUBLE PRECISION`, `TIMESTAMP WITH TIME ZONE`. For JSON columns use the Flyway
  placeholder `${json_type}` (PostgreSQL `JSONB`, H2 `JSON`, configured in
  `application.yml` / `application-test.yml`).
- Entity `@UniqueConstraint` / `@Index` annotations are documentation only; keep their
  names identical to the migration.

## Type and identity policy

- Time: Java `Instant` (UTC) ↔ `TIMESTAMP WITH TIME ZONE`. Requests may carry an offset;
  storage and responses are UTC. Athlete `timezone` is for presentation only.
- Internal PK (`BIGINT` identity) is never an external service id. External identity is
  the pair `external_source` (`GARMIN | INTERVALS_ICU | MANUAL`) + `external_id`, unique
  on both `activity` and `activity_raw`.
- Raw external payloads are stored as JSONB (`@JdbcTypeCode(SqlTypes.JSON)` on a
  `JsonNode`); no extra JSON type libraries.
- Optional metrics are nullable; do not use 0 as "unknown". Prefer the existing Java type
  (`Integer`, `Double`) over oversized numeric types.
- Audit fields via Spring Data auditing: `created_at` (never updated) and, where present,
  `updated_at`.

## activity vs activity_raw

| table | meaning | rules |
|-------|---------|-------|
| `activity` | RunningAI's normalised record (type, start, duration s, distance m, HR) | one row per external identity; ingestion updates it in place (same id, same `created_at`) |
| `activity_raw` | the untouched external payload (`payload` JSONB, `fetched_at`) | one row per external identity; a re-fetch replaces `payload` + `fetched_at`, keeps id and `created_at`; `activity_id` is **nullable** so the raw row can exist before / without a normalised activity (raw-first); no version history |

Do not widen `activity` with every external field; unmapped data belongs in `activity_raw`
and can be re-mapped later.

## Tests

- Default suite runs on H2 (PostgreSQL mode) with the real Flyway migrations
  (`SchemaMigrationTest` checks the history, tables, JSON column and unique constraints).
- Known H2 differences: `JSON` instead of `JSONB`; timestamps rounded to microseconds.
  Assert timestamps at millisecond precision when comparing a round-tripped value.
- Identity ids make `save()` insert immediately, so constraint violations surface at
  `save()`/`flush()`; wrap both in the assertion.
- For DB-specific work, also run the suite against real PostgreSQL when one is
  available (Docker Compose on the main PC, or any local instance) by overriding the
  datasource, e.g. `SPRING_APPLICATION_JSON` with the `running_ai_test` database and
  `spring.flyway.placeholders.json_type=JSONB`. Do not force Testcontainers on machines
  without Docker; record in the work order whether PostgreSQL verification ran.
- Never run Flyway against a production database from a hook or script.
