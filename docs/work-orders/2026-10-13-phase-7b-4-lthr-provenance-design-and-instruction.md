# WO-RUNNINGAI-PHASE-7B-4 — Garmin Lactate Threshold Provenance & 변경 이력 (설계 + 구현 작업지시서)

상태: **설계 승인 대기** (이 문서가 산출물; 구현은 승인 후 별도 수행). 운영 DB/Flyway 적용·
운영 재시작·Funnel 변경은 이 Phase 전체에서 금지 유지.

## A. 7B-3 설계·현행 구조 검토 (구현 전 확인 결과)

| 현행 | 사실 |
|---|---|
| `athlete_intensity_profile`(V5) | 현재값 2컬럼 + created/updated_at뿐 — 출처·이력·측정일 없음. in-place 갱신(의도된 설계) |
| `GarminLactateThresholdMapper`/`Snapshot` | bpm·pace만 정규화 — **커넥터 응답의 `speed_and_heart_rate.calendarDate`(측정 시각)·`version`을 버림** (7B-4의 1차 복구 대상) |
| `mergeGarminSnapshot` | null=미보고(보존), 동일값=무기록 — 이력 테이블이 없어 "조회했으나 동일" 사실도 소실 |
| `replaceDefaultProfile` | 수동 PUT — GARMIN 경로와 구분 저장 안 됨 |
| `LactateThresholdProvenanceV2`(7B-3) | `sourceTracked=false` 고정 + 경고문 — 본 Phase가 true 조건을 만드는 대상 |
| 실데이터 | 현재 176/290은 정황상 10-05 profile-sync 결과지만 **DB로 증명 불가** → 7B-4 이후에도 이 행의 출처는 "미확인"으로 보존해야 함(요구 4) |
| calendarDate 형식 | `"2026-10-06T00:50:55.648"` — **오프셋 없는 로컬 시각, 타임존 미문서화**. UTC로 추정 변환 금지 원칙과 충돌하므로 Instant 변환 불가 |

## B. 스키마 설계 — V23 `athlete_intensity_profile_history` (append-only)

7B-2 `injury_report`와 동일한 원장 패턴. 기존 테이블은 **무변경**(V5 불변, ALTER 없음).

```sql
CREATE TABLE athlete_intensity_profile_history (
    id                                     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    athlete_id                             BIGINT                   NOT NULL,
    source                                 VARCHAR(16)              NOT NULL, -- 'MANUAL' | 'GARMIN'
    applied                                BOOLEAN                  NOT NULL, -- false = 관측만(값 동일), 프로필 미변경
    lactate_threshold_heart_rate_bpm       INTEGER,                           -- 이 이벤트 시점의 적용/관측 값
    lactate_threshold_pace_seconds_per_km  INTEGER,
    previous_heart_rate_bpm                INTEGER,                           -- 직전 적용값(최초 생성 시 NULL)
    previous_pace_seconds_per_km           INTEGER,
    garmin_calendar_date_raw               VARCHAR(40),                       -- GARMIN만: calendarDate 원문 그대로
    garmin_fetched_at                      TIMESTAMP WITH TIME ZONE,          -- GARMIN만: RunningAI 수집 시각(UTC)
    recorded_at                            TIMESTAMP WITH TIME ZONE NOT NULL, -- 서버 기록 시각(UTC)
    CONSTRAINT fk_profile_history_athlete FOREIGN KEY (athlete_id) REFERENCES athlete (id),
    CONSTRAINT ck_profile_history_source CHECK (source IN ('MANUAL','GARMIN'))
);
CREATE INDEX idx_profile_history_athlete_recorded ON athlete_intensity_profile_history (athlete_id, recorded_at DESC);
```

설계 근거:
- **측정일 vs 수집일 분리(요구 1)**: `garmin_calendar_date_raw`는 타임존이 미문서화라 **원문
  VARCHAR 보존**(추정 변환 금지 — 6D speed 단위 원칙과 동일), `garmin_fetched_at`은 우리가
  아는 UTC Instant.
- **이력(요구 2)**: 변경은 항상 새 행(applied=true, previous_* 포함). 행 수정·삭제 없음.
- **출처 구분(요구 3)**: `source` — `replaceDefaultProfile`→MANUAL, `mergeGarminSnapshot`→GARMIN.
  동일값 관측(GARMIN 폴링이 같은 값 재보고, MANUAL PUT이 동일값 재입력)도 **applied=false로
  기록** — "Garmin이 날짜 X에 같은 값을 재확인했다"는 신선도 증거를 보존(스케줄러는 계속
  기본 off라 행 증가 걱정 없음, 수동 트리거뿐).
- **기존 데이터 보존(요구 4)**: 백필 없음. 현행 176/290 행은 이력 0건 상태로 남고 아래 C
  규칙에 의해 계속 `sourceTracked=false` — 가짜 출처를 만들어내지 않는다.

## C. provenance 판정 규칙 (요구 5)

`sourceTracked=true`는 **오직**: 최신 `applied=true` 이력 행이 존재하고 그 행의
(bpm, pace)가 현재 `athlete_intensity_profile` 값과 **정확히 일치**할 때. 그 행의 `source`가
provenance의 source가 된다. 불일치(이력 밖 수정 등 비정상)·이력 없음 → `false` + 기존 경고
유지. 추가 노출(원산지 주장 없이 신선도만 주는 필드): `lastGarminObservation`
(= 최신 GARMIN 행의 calendar_date_raw/fetched_at, applied 무관) — "출처는 미확인이지만
Garmin이 10-06에 같은 값을 보고했다"를 표현 가능.

## D. 재계산 정책 (요구 6 — 설계 결정)

**LTHR 변경 시 과거 분석 자동 재계산 금지.** 근거: `activity_analysis.lthr*_seconds`는
"그 시점 설정으로 계산된 측정"이고 `computed_at`+`analysis_version`이 이미 영속된다 —
자동 소급 재계산은 과거 보고서·코치 스냅숏과의 불일치를 조용히 만든다. 정책:
1. 자동 트리거 0 (기존 원칙 유지: 재분석은 명시적 `POST /activities/{id}/analysis`뿐).
2. provenance에 `lastAppliedChangeAt`(최신 applied=true recorded_at)을 노출 — 소비자
   (코치/MCP)가 `analysis.computedAt < lastAppliedChangeAt`이면 "이 분석의 LTHR 노출 지표는
   이전 기준으로 계산됨"을 스스로 식별 가능. 프롬프트 가이드에 1문장 추가.
3. 운영 플레이북(문서)으로만: 큰 LTHR 변경 후 원하는 활동을 수동 재분석.

## F. 마이그레이션 영향 보고

- **V23 1건, 순수 가산**(CREATE TABLE + INDEX). 기존 테이블 ALTER 0 — V5~V22 전부 불변.
- H2(PostgreSQL 모드) 호환 타입만 사용(기존 V21 패턴 그대로) — 테스트 스위트 즉시 적용 가능.
- **운영 적용 시점**: 이 Phase에서는 미적용(개발/H2·사본 검증만). 운영 반영은 7C-2 체크리스트
  B의 V21/V22와 **함께 V23까지 한 번에** 적용하는 것을 권고(재기동 1회로 통합). 적용 직후
  이력은 비어 있으므로 운영 `sourceTracked`는 다음 실제 변경 또는 Garmin 재감지까지 false
  유지 — **이것이 올바른 동작**(요구 4·5).
- 데이터 이행/백필: 없음(의도적). 롤백: 테이블 DROP만으로 복구 가능(다른 스키마 무의존).

## G. 구현 STEP (승인 후 실행 순서)

1. V23 + 엔티티/리포지토리(append-only, injury_report 패턴) + `SchemaMigrationTest` 갱신
2. Mapper/Snapshot calendarDateRaw + 단위 테스트(원문 보존·널 안전)
3. ProfileService 이력 기록 + provenance 판정 + 시그니처 전파(SyncService) + 단위/영속 테스트
4. V2 provenance 가산 필드 + 직렬화/빌더 테스트 + 프롬프트 지침 1-2문장
5. MCP `get_athlete_profile` 반영 + read 스위트 갱신
6. 전체 회귀 1회 → 문서(result) → main-3 커밋 (origin push 금지)

완료 기준: 위 테스트 전부 + "값을 바꾸지 않은 Garmin 재관측"과 "실제 변경"이 이력에서
구분되고, sourceTracked가 규칙 C로만 true가 되며, 기존 176/290의 출처가 날조되지 않을 것.
