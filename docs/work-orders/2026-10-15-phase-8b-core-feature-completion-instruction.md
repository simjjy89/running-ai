RunningAI — Core Feature Completion Master Work Order

0. 역할 및 최종 목표

당신은 RunningAI의 시니어 백엔드 아키텍트, 개발 리드, DevOps 엔지니어 및 QA 책임자다.

이제부터 개별 Phase마다 사용자에게 승인받는 방식이 아니라, 하나의 개발 목표를 달성할 때까지 설계·구현·테스트·개선을 자율 반복하는 방식으로 작업한다.

최종 목표

RunningAI를 실사용 가능한 개인 러닝 코칭 시스템으로 완성한다.

목표 사용자 경험:

1. Garmin 활동과 회복 데이터가 자동으로 수집된다.
2. RunningAI가 러닝 성과·피로·회복·부상 상태를 분석한다.
3. AI Coach가 최신 데이터를 기반으로 훈련 초안을 생성한다.
4. 사용자가 자연어로 훈련을 수정하고 승인한다.
5. 승인된 훈련을 안전하게 Intervals.icu에 게시할 수 있다.
6. 훈련이 Garmin에 전달되었는지 확인할 수 있다.
7. 오늘의 AI 훈련이 Garmin 워치페이스에 표시된다.
8. 사용자가 ChatGPT에서 이 기능들을 이용한다.

단, 외부 서비스가 제공하지 않는 기능을 구현된 것처럼 보고하지 않는다.

3. 개발 범위

Workstream A — Garmin 동기화 안정화

목표

기존 Garmin 자동 동기화 기능을 운영에 적용할 수 있을 정도로 안전하게 만든다.

현재 상태:

* 증분 동기화 구현
* 7일 overlap
* raw-first
* 중복 방지
* ReentrantLock
* 실패 이력 V27 적용
* Garmin 활동 스케줄러 OFF
* 운영 수동 동기화 미실행

구현 과제

1. 기존 garmin_sync_attempt를 활용한 자동 차단 정책
2. 인증 실패와 rate limit 실패의 구분
3. 연속 실패 임계값 관리
4. PARTIAL 처리 시 실패 카운터 정책 명확화
5. 스케줄러 중단·복구 정책
6. 프로세스 강제 종료로 인한 미완료 시도 식별 방안
7. 중복 수집과 동시 실행 방지 회귀 검증
8. Garmin 요청량 제한 및 백필 충돌 방지

자동 차단이 실제 동기화 성공을 잘못 방해하지 않도록 단위·통합 테스트를 작성한다.

운영 스케줄러를 실제로 켜지 않는다.

완료 기준

* 정상 동기화 유지
* 401/429 안전 차단
* 연속 실패 정책 검증
* 재기동 이후 상태 일관성
* 기존 체크포인트 불변성
* PostgreSQL 통합 테스트 PASS

Workstream B — API 예외 처리 수정

현재 결함

* 존재하지 않는 경로: 404 정상
* 미지원 HTTP 메서드: 500 오류
* 필수 요청 파라미터 누락: 500 오류

구현

기존 응답 계약을 유지한다.

{code, message, timestamp}

다음을 수정한다.

1. HttpRequestMethodNotSupportedException → 405
2. MissingServletRequestParameterException → 400
3. Allow 헤더 보존
4. 정상 404 동작 유지
5. 예상 가능한 클라이언트 오류는 WARN 이하로 처리
6. 불필요한 ERROR 스택 트레이스 제거
7. 기존 GlobalExceptionHandler와 충돌하지 않도록 구현
8. 관련 테스트와 주석 정정

다른 API 예외까지 무분별하게 리팩터링하지 않는다.

Workstream C — AI 훈련 게시 신뢰성

현재 상태

* Draft 생성·수정·승인 구현
* 운영 게시 성공 3건
* 중복 게시 방지 구현
* 운영 게시 기능 비활성
* 게시 실패 시도 이력 미구현

구현

Flyway V29 예약 상태를 우선 확인한다.

V29__create_workout_draft_publish_attempt.sql

기존 게시 실패 이력 설계 문서를 재사용하되 실제 운영 DB에 적용하지 않는다.

구현 과제:

1. 게시 시도 이력 저장
2. 성공·실패·재시도 상태 기록
3. 외부 요청과 응답의 안전한 메타데이터 저장
4. 네트워크 타임아웃 처리
5. 성공 여부가 불명확한 외부 게시의 중복 방지
6. 기존 게시 기록과의 정합성
7. 게시 이력 조회
8. 민감정보 로그 차단

중요

외부 게시 재시도는 중복 워크아웃을 생성할 위험이 있다.

요청 결과가 불확실한 상태에서는 무조건 다시 POST하지 말고, 조회를 통한 결과 확인 또는 보수적 중단 정책을 적용한다.

기존 publish_approved_draft의 접근 차단은 유지한다.

Workstream D — AI Draft → Watchface 연동

목표

현재 워치페이스가 레거시 today_plan.json 또는 Intervals.icu 직접 조회에 의존하는 문제를 해결한다.

RunningAI에서 승인된 훈련을 Relay를 통해 워치페이스에 표시하도록 연결한다.

구현 과제

1. Spring 승인 Draft 조회 계약 확인
2. 기존 Watchface Relay API 분석
3. Spring → Relay 데이터 변환
4. 기존 워치페이스 응답 계약 유지
5. REST DAY 지원
6. 승인된 훈련이 없는 상태 처리
7. 데이터 갱신 주기
8. 오래된 훈련 정보 표시 방지
9. Relay 오류 시 안전한 fallback
10. 민감정보 노출 방지

기존 워치페이스 UI의 디자인이나 폰트는 변경하지 않는다.

별도 Watchface 저장소에 접근할 수 있다면 필요한 연동 코드와 테스트까지 구현한다.

접근할 수 없다면 서버 측 호환성 구현과 실제 기기 검증 계획을 완성하고, 실기기 검증만 미완료로 남긴다.

실제 기기 설치·펌웨어 배포는 승인 없이 진행하지 않는다.

⸻

Workstream E — Garmin 훈련 도달 검증

목표

Intervals.icu에 게시된 훈련이 Garmin Connect 및 FR265에 전달되었는지 확인하는 방법을 마련한다.

구현

1. 현재 Intervals.icu 연동 방식 확인
2. Python garminconnect 버전 확인
3. 예정 워크아웃 조회 지원 여부 확인
4. 지원될 경우 읽기 전용 조회 구현
5. Intervals 일정과 Garmin 일정의 대응 관계 검토
6. 도달 상태와 조회 불가 상태 구분
7. 실패 시 사용자에게 명확한 상태 제공

Garmin 예정 워크아웃 조회 API가 지원되지 않거나 불안정하면 억지로 비공식 쓰기 API를 개발하지 않는다.

실현 불가능한 경우 그 사유와 수동 확인 절차를 문서화한다.

8. 훈련 분석 리포트 생성

현재 확보되지 않은 1년 데이터를 임의로 생성하거나 보간하지 않는다.

훈련 생성

기존 EASY / RECOVERY / LONG 구조를 보호하면서 다음 기능을 검토·구현한다.

* QUALITY 훈련 표현

결정론적 추천 엔진이 임의로 고강도 운동을 자동 선택하도록 변경하지 않는다.

AI Coach의 자동 호출은 테스트 Fixture 또는 모의 응답을 기본으로 한다. 실제 유료 모델 호출은 기존 승인된 범위에서만 수행한다.

5. 개발 실행 방식

다음 순서로 내부 작업을 진행한다.

1. 저장소·브랜치·기존 변경 사항 확인
2. 이미 구현된 기능을 식별하고 중복 구현 제외
3. 필요한 최소 설계 작성
4. Workstream별 코드 구현
5. 신규 테스트 작성
6. 실패 테스트 수정
7. 개발 PostgreSQL 통합 검증
8. 다른 Workstream 계속 진행
9. 전체 회귀 테스트
10. 전체 기능 통합 검증
11. 코드 리뷰 및 품질 개선
12. 최종 문서 작성
13. 최종 결과 보고

중간 작업 완료마다 사용자 승인을 요청하지 않는다.

진행 상황은 개발 문서에 기록하며, 격리된 작업 브랜치에 의미 있는 단위로 로컬 커밋한다.

필요하면 내부적으로 여러 Phase와 커밋으로 나눌 수 있지만, 사용자가 별도 요청하지 않는 한 하나의 마스터 작업으로 계속 진행한다.

테스트 실패가 발생하면 원인을 조사하고 수정 후 재실행한다.

단, 안전한 해결이 불가능하거나 승인 금지 영역을 변경해야 한다면 해당 작업을 보류한다.
